# 调度之眼 (Console App-LZ) — 产品需求与测试套件说明书 (PRD)

> **文档版本**：v1.1.0  
> **编写时间**：2026-08-26  
> **定位**：调度中枢全功能可视化集成测试与微服务治理工作台

---

## 1. 产品背景与业务痛点

在企业级数据流通与隐私治理架构中，`services/service-hub` 是连接底层数据源、智能分类分级引擎与不可篡改存证系统的"中枢神经"。然而，在开发、调试与运维过程中面临以下痛点：
1. **测试断层**：以往测试 `service-hub` 依赖编写长篇 Go 测试用例或复杂的 `curl` 命令，缺少端到端全链路即时可视化手段。
2. **状态黑盒**：数据在 6 大阶段（Ingest ➔ Fetch ➔ Classify ➔ Desensitize ➔ Return ➔ Audit）中的耗时、分流逻辑、分类评级与脱敏前后对比缺乏直观展示。
3. **Phase B 租约并发不可视**：多副本 `service-hub` 抢占 PostgreSQL 任务时的行锁 (`FOR UPDATE SKIP LOCKED`)、租约续期与崩溃接管难以在 UI 上实时监测。

**`console/app-lz`** 应运而生，作为专属于 `service-hub` 的全景治理与测试控制台，打通四大服务，让调度全流程"看得见、摸得着、测得透"。

---

## 2. 用户角色与核心用户旅程

### 2.1 核心角色
- **开发与测试工程师 (Developer / QA)**：一键执行 TS-01~TS-07 全量场景自动化测试，验证流水线与微服务协同稳定性。
- **架构师与运维工程师 (Architect / SRE)**：实时监控微服务网格拓扑、Phase B 租约争抢状态、QPS 与 P50/P90/P95/P99 延迟分布，定位长尾瓶颈。
- **安全与合规审计员 (Compliance Auditor)**：查看任务脱敏前后对比，并对 `audit-log` 的 Merkle 树哈希链进行一键验真。

### 2.2 核心用户旅程
1. **拓扑探查**：打开 App-LZ 首页，秒级确认 4 大服务（Hub, Datasource, Audit, Agent）物理连接与 RTT。
2. **流水线调度**：在流水线大屏中选择数据源切片或输入测试数据，点击"触发调度"，实时观看数据在 6 个阶段间流动，对比原始数据与脱敏数据。
3. **自动化测试**：切换至"自动化测试"工作台，点击"运行全部套件"，查看 7 大预设用例实时运行动效与断言结果，导出测试报告。
4. **性能调优**：进入"性能监控"面板，观察高并发压测下的阶段耗时瀑布图与分位数分布，指导参数调优。

## 3. 功能需求详细规格 (FR)

### 3.1 模块一：四微服务固定网格拓扑与双协议健康矩阵 (Topology & Mesh Health)
- **FR-1.1**：固定顺序展示 4 大服务节点拓扑图：`1. 调度中枢 ➔ 2. 隐私与分类引擎 ➔ 3. 数据源管理 ➔ 4. 脱敏审计日志`。
  - *验收标准*：无论异步探测响应顺序如何，页面卡片物理展示顺序始终严格按 `#1` ~ `#4` 渲染，不可乱序。
- **FR-1.2**：支持 REST (HTTP/1.1 JSON) 与 gRPC (HTTP/2.0 mTLS Protobuf) 双协议视图即时切换。
  - *验收标准*：切换协议工具栏时，卡片端点地址、主视图状态与延迟数值即时同步切换至对应协议通道数据。
- **FR-1.3**：卡片实时展示各服务的状态（Ready / Unhealthy / Offline）、双通道往返延时 RTT (ms)、版本号与健康详情。
  - *验收标准*：RTT 数值与实际网络探测延迟偏差 < 5ms。
- **FR-1.4**：提供一键并发深度探针（Refresh Probe）按钮，主动并发探测 4 大微服务。
  - *验收标准*：点击后 2 秒内完成全部 4 节点探测并平滑更新 UI。
- **FR-1.5**：单个服务不可达时，该节点标记为 `Offline`（红色），其余节点正常展示，不阻塞整体响应。
  - *验收标准*：任一上游服务宕机后，拓扑面板正确标记单点故障，整体集群状态标记为 `Degraded`。

### 3.2 模块二：6 阶段流水线动态大屏 (6-Stage Pipeline Visualizer)
- **FR-2.1**：渲染 6 阶段流程图（`Ingest` ➔ `Fetch` ➔ `Classify` ➔ `Desensitize` ➔ `Return` ➔ `Audit`）。
  - *验收标准*：6 个阶段节点水平排列，阶段间有流向箭头，当前活跃阶段高亮。
- **FR-2.2**：支持手动构建自定义 JSON 请求体，或一键加载常用预设（医保报销、康养生命体征、高敏病历）。
  - *验收标准*：预设加载后自动填充 JSON 编辑器，字段完整可提交。
- **FR-2.3**：任务提交后，流程图展示动态水流/光点流转动效，各阶段展示耗时。
  - *验收标准*：任务进入某阶段时该节点亮起动效，完成后显示该阶段耗时（ms）。
- **FR-2.4**：展示数据脱敏前 vs 脱敏后的 JSON/表格双栏对比，并标出命中等级与分类规则。
  - *验收标准*：左右两栏分别展示原始/脱敏数据，差异字段高亮，顶部展示分类等级（如 `L3 → k_anon`）。

### 3.3 模块三：任务全生命周期与租约看板 (Task Lifecycle & Lease Inspector)
- **FR-3.1**：任务列表支持表格视图，展示 Task ID、状态 Badge、当前阶段、数据源、操作类型、创建/完成时间、耗时。
  - *验收标准*：列表支持分页（默认 100 条/页，上限 1000），列排序。
- **FR-3.2**：支持按状态筛选（全部 / 等待中 / 运行中 / 已完成 / 失败）与关键词模糊搜索。
  - *验收标准*：筛选响应时间 < 500ms（1000 条数据量级）。
- **FR-3.3**：点击任务行弹出详情抽屉，展示完整输入、输出、重试次数及错误日志。
  - *验收标准*：抽屉从右侧滑出，展示原始 JSON 输入/输出，错误信息红色高亮。
- **FR-3.4**：**Phase B 租约专区**：展示 PostgreSQL 租约持有者 Worker ID、租约有效倒计时进度条、崩溃回收计数。
  - *验收标准*：PostgreSQL 后端时展示完整租约信息；SQLite/内存后端时显示提示信息"租约调度需 PostgreSQL 后端"并隐藏专有指标。

### 3.4 模块四：一键全场景自动化测试执行器 (One-Click E2E Test Suite Runner)
- **FR-4.1**：内置 7 大核心场景用例（TS-01 基础分发、TS-02 自适应分类、TS-03 数据源切片、TS-04 审计验真、TS-05 熔断恢复、TS-06 高并发分位数压测、TS-07 Phase B 租约争抢）。
  - *验收标准*：测试列表展示所有 7 个用例的名称、描述、前置条件标签。
- **FR-4.2**：支持单选/全选用例执行，实时展示用例执行耗时与断言详情（预期值 vs 实际值）。
  - *验收标准*：每个断言结果展示 `expected` vs `actual`，通过为绿色、失败为红色。
- **FR-4.3**：支持控制台实时日志输出（Terminal 风格暗色日志窗口）。
  - *验收标准*：日志通过 SSE 实时推送，延迟 < 500ms，支持自动滚动与手动暂停。
- **FR-4.4**：支持一键导出 Markdown 测试执行报告。
  - *验收标准*：导出文件包含执行时间、用例列表、每个断言的通过/失败详情、总结统计。

### 3.5 模块五：数据源资产探查器 (Datasource Explorer)
- **FR-5.1**：列表展示 `ds_yibao` 与 `ds_kangyang` 的元数据、字段名、类型与敏感度标签。
  - *验收标准*：字段列表展示字段名、数据类型、敏感度标注（L1~L5）。
- **FR-5.2**：支持在线切片拉取（1~100 条），表格化预览原始数据。
  - *验收标准*：输入 limit 值后 2 秒内返回数据并渲染表格。
- **FR-5.3**：支持选中特定切片行，一键派发至 `service-hub` 流水线进行实时脱敏。
  - *验收标准*：点击"派发"后自动跳转至流水线大屏，任务 ID 出现在活跃任务列表中。

### 3.6 模块六：不可篡改审计与 Merkle 验真 (Audit & Merkle Verifier)
- **FR-6.1**：展示 `audit-log` 记录的流水线存证流水（时间、Task ID、数据哈希、操作人、加密算法）。
  - *验收标准*：审计列表支持分页与按时间倒序排列。
- **FR-6.2**：提供"一键 Merkle 验真"按钮，调用验证接口并以树状图或证明链形式展示验真结果。
  - *验收标准*：验真结果展示根哈希、验证通过/失败状态、参与验证的叶子节点数。

### 3.7 模块七：性能监控与耗时直方图 (Metrics & Performance)
- **FR-7.1**：展示实时 QPS 吞吐量折线图。
  - *验收标准*：折线图每 5 秒自动刷新，展示最近 5 分钟的 QPS 趋势。
- **FR-7.2**：展示 6 阶段平均耗时柱状图/瀑布图，标示最大性能耗时阶段。
  - *验收标准*：耗时最长阶段以红色高亮标注。
- **FR-7.3**：展示 P50 / P90 / P95 / P99 延迟分布指标卡片与名词解释。
  - *验收标准*：指标卡片数值与 Prometheus 查询结果偏差 < 5%，悬停展示分位数含义解释。

## 4. 非功能性需求 (NFR)

### 4.1 性能需求

| 指标 | 目标值 | 测量方式 |
|---|---|---|
| 前端首屏加载时间 (FCP) | < 1.5 秒 (本地开发) / < 3 秒 (生产构建) | Lighthouse / Chrome DevTools |
| 前端交互响应延迟 | < 100ms (UI 操作反馈) | 用户感知 |
| BFF API 响应时间 (直通转发) | < 上游响应时间 + 10ms | BFF 结构化日志 `latency_ms` |
| BFF API 响应时间 (聚合查询) | < 最慢上游响应时间 + 50ms | BFF 结构化日志 `latency_ms` |
| SSE 日志流推送延迟 | < 500ms (从事件产生到前端渲染) | 前端时间戳对比 |
| 拓扑自动刷新周期 | 30 秒 (可配置) | 前端定时器 |

### 4.2 可用性需求

| 场景 | 降级策略 |
|---|---|
| 单个上游服务不可达 | 拓扑面板标记 `unreachable`，其余功能正常；直通接口返回 502 错误 |
| BFF 自身不可达 | 前端展示"后端连接失败"提示，提供重试按钮 |
| SSE 流中断 | 前端自动重连（指数退避，最大 3 次，间隔 1s/2s/4s） |
| 所有上游服务不可达 | 拓扑面板全部标红，测试执行器标记所有用例为 FAIL |

### 4.3 兼容性需求

| 维度 | 支持范围 |
|---|---|
| 浏览器 | Chrome 120+、Firefox 120+、Edge 120+、Safari 17+ |
| 分辨率 | 最低 1280×720，推荐 1920×1080，响应式适配 |
| 深色模式 | 支持浅色/深色主题切换，跟随系统偏好或手动选择 |

### 4.4 可访问性需求

| 维度 | 要求 |
|---|---|
| 键盘导航 | 所有交互元素可通过 Tab 键聚焦，Enter/Space 触发 |
| 语义化 HTML | 使用语义化标签（`nav`、`main`、`section`），图标配备 `aria-label` |
| 颜色对比度 | 文本与背景对比度 ≥ 4.5:1 (WCAG AA) |

### 4.5 国际化需求

- 完整支持 `zh-CN` / `en-US` 双语切换
- 所有用户可见文本通过 i18n 字典管理，无硬编码字符串
- 日期时间格式跟随语言设置（中文：`YYYY-MM-DD HH:mm:ss`，英文：`MMM DD, YYYY HH:mm:ss`）

## 5. 测试套件详细定义 (Test Suite Specification)

### 5.1 测试用例通用结构

每个测试用例遵循以下声明式定义结构：

```go
type TestCase struct {
    ID          string        // 用例编号 (TS-01 ~ TS-07)
    Name        string        // 用例名称
    Description string        // 测试目的描述
    Prereqs     []string      // 前置条件列表
    Steps       []TestStep    // 执行步骤
    Timeout     time.Duration // 整体超时
    Tags        []string      // 标签 (smoke / e2e / perf / lease)
}

type TestStep struct {
    Action     Action        // 执行动作 (HTTP 请求 / 等待 / 故障注入)
    Assertions []Assertion   // 断言列表
}

type Assertion struct {
    Type     string // "status_code" | "json_path" | "field_exists" | "poll_until"
    Expected any    // 预期值
    Actual   any    // 实际值（执行后填充）
    Passed   bool   // 是否通过（执行后填充）
    Message  string // 断言描述
}
```

### 5.2 测试用例详细规格

|---|---|
| **目的** | 验证 `POST /api/hub/dispatch` 基础 Mask 任务分发与 6 阶段流水线完整执行 |
| **前置条件** | 4 服务全部在线 |
| **标签** | `smoke`, `e2e` |
| **超时** | 30 秒 |

| 步骤 | 动作 | 断言 |

| 1 | `POST /api/hub/dispatch` (source=ds_yibao, operation=mask, payload=含身份证号) | HTTP 202, `$.status == "accepted"`, `$.task_id` 非空 |
| 2 | 轮询 `GET /api/hub/tasks/{task_id}` (间隔 500ms) | `$.status == "completed"` 在 30 秒内 |
| 3 | 校验任务详情 | `$.stage == "done"`, `$.duration_ms > 0`, `$.error` 为空 |

#### TS-02: 自适应分类与自动策略路由

|---|---|

| **目的** | 验证从 `datasource-mgr` 自动抓取数据并触发完整流水线 |
| **前置条件** | 4 服务全部在线 |
| **标签** | `e2e` |
| **超时** | 60 秒 |

| 步骤 | 动作 | 断言 |
|---|---|---|
| 1 | `POST /api/hub/pipeline/trigger-datasource` (datasource_id=ds_yibao, limit=10) | HTTP 202, 返回批量 task_id 列表 |

#### TS-04: 全链路审计存证与 Merkle 验真

| 属性 | 值 |
|---|---|
| **目的** | 验证流水线处理完数据后审计存证正确写入且 Merkle 链可验真 |
| **前置条件** | 4 服务全部在线，先执行 TS-01 产生至少一条存证 |
| **标签** | `e2e` |

| 步骤 | 动作 | 断言 |
|---|---|---|
| 1 | 等待 TS-01 任务完成 | `$.status == "completed"` |

| 3 | `POST /api/audit/snapshots/verify` | `$.merkle_valid == true`, `$.root_hash` 非空 |

#### TS-05: Agent 宕机熔断与降级测试

| 属性 | 值 |
|---|---|
| **目的** | 验证上游 Agent 不可达时 Hub 熔断器正确触发，恢复后自动恢复 |
| **前置条件** | 4 服务全部在线，需启用故障注入模式 (`PRIVACY_TEST_FAULT_INJECT=1`) |
| **标签** | `e2e`, `resilience` |
| **超时** | 60 秒 |

| 步骤 | 动作 | 断言 |
|---|---|---|
| 1 | 激活故障注入（模拟 Agent 超时） | 故障注入 API 返回 200 |
| 2 | `POST /api/hub/dispatch` 触发任务 | 任务最终 `$.status == "failed"`，错误信息包含 "timeout" 或 "circuit breaker" |
| 3 | 检查 Hub 状态 | `GET /api/hub/status` 返回 `$.agent_status` 为 "unreachable" 或熔断状态 |
| 4 | 恢复故障注入 | 故障注入 API 返回 200 |
| 5 | 等待恢复 + 再次探测 | `GET /readyz` 返回 200，Agent 状态恢复为 "ok" |

#### TS-06: 高并发吞吐量与延迟压测

| 属性 | 值 |
|---|---|
| **目的** | 验证高并发下调度中枢的吞吐量与延迟分布 |
| **前置条件** | 4 服务全部在线，建议关闭 LLM 层避免瓶颈 |
| **标签** | `perf` |
| **超时** | 120 秒 |
| **参数** | `concurrency` (默认 50), `benchmark_requests` (默认 100) |

| 步骤 | 动作 | 断言 |
|---|---|---|
| 1 | 并发发送 N 个 `POST /api/hub/dispatch` 请求 | 全部请求返回 202 或 429 |
| 2 | 等待所有任务完成 | 全部任务在 120 秒内完成 |
| 3 | 统计性能指标 | 输出 QPS、成功率、P50/P90/P95/P99/Avg/Min/Max 延迟 |
| 4 | 校验性能基线 | 成功率 > 95%，P99 < 5000ms |

#### TS-07: Phase B 租约多副本并发争抢

| 属性 | 值 |
|---|---|
| **目的** | 验证 PostgreSQL 后端下多 Hub 副本并发任务认领无重复、无死锁 |
| **前置条件** | **需 PostgreSQL 后端** + 至少 2 个 Hub 副本运行 |
| **标签** | `lease`, `e2e` |
| **超时** | 60 秒 |

| 步骤 | 动作 | 断言 |
|---|---|---|
| 1 | 批量创建 50 个待处理任务 | 全部返回 202 |
| 2 | 等待所有任务被认领并完成 | 全部 50 个任务 `$.status == "completed"` |
| 3 | 校验无重复执行 | 每个 task_id 仅被一个 worker 执行（通过租约日志验证） |
| 4 | 校验无死锁 | 无任务因死锁而 `$.status == "failed"` |

## 6. 约束与假设

### 6.1 约束
1. App-LZ 不直接操作数据库，所有数据通过 4 个上游服务的 REST/gRPC 接口获取。
2. BFF 层不持久化任何业务数据（测试执行记录仅保存在内存中，BFF 重启后丢失）。
3. 前端不直接连接上游服务，所有请求必须经过 BFF 层。

### 6.2 假设
1. 4 个上游服务在测试执行期间保持运行（除 TS-05 故障注入场景）。
2. `service-hub` 使用 SQLite 后端时，TS-07 租约争抢测试自动跳过。
3. 网络延迟在本地开发环境下 < 10ms，不影响超时类断言的准确性。
4. `engine` Agent 的 LLM 层默认关闭（`PRIVACY_LLM_ENABLE=false`），避免分类延迟影响测试耗时。
