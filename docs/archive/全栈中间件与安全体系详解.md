## 第1章 TraceID 自动注入与 Header 传递

### 1.1 为什么需要这个机制？

在微服务架构中，一个前端请求可能要经过：

```
前端 → BFF → Service-Hub → Engine (gRPC)
                ↓
         Datasource-Mgr / Audit-Log
```

如果没有统一的追踪 ID，当请求出错或性能异常时，你需要分别去 5 个服务的日志里翻找，而且**无法确定哪些日志条目属于同一次用户请求**。

**TraceID 的作用**：给每一次用户请求发一个"身份证号"，所有参与处理的服务都在日志中带上这个 ID，这样就能跨服务、跨时间地把一次请求的完整生命周期串联起来。

### 1.2 双头设计：X-Request-ID + X-Trace-ID

文档中提到使用**双头下发**，这是为了区分两个不同层面的标识：

| Header | 生成方 | 用途 | 生命周期 |
|:---|:---|:---|:---|
| **`X-Request-ID`** | 前端/BFF 入口层 | **业务请求标识**。一次用户操作（如点击"脱敏"按钮）的唯一 ID | 从前端发起，贯穿到最底层服务 |
| **`X-Trace-ID`** | 中间件自动补充 | **追踪标识**。用于 OpenTelemetry/Jaeger 等追踪系统的 Span 关联 | 与 Request-ID 保持一致或衍生 |

> 实际场景中，两者通常设置为同一个值（或 Trace-ID 继承 Request-ID），形成**单调不丢失**的追踪链。

### 1.3 自动注入：请求没有带 ID 怎么办？

**自动注入**的意思是：中间件会检查每个进入系统的 HTTP/gRPC 请求，如果请求头里没有 `X-Request-ID`，就**自动生成一个**并注入到上下文中。

```
用户请求 ──▶ [TraceMiddleware] 检查 Header
                │
                ├─ 有 X-Request-ID？──▶ 直接复用，向后传递
                │
                └─ 没有？──▶ 生成新 ID（如 req-1787554500-abc12345）
                              └── 写入响应头 X-Request-ID，让前端也知道
```

**代码层面（Go 中间件）**：
```go
// pkg/middleware/trace.go
func TraceMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        reqID := c.GetHeader("X-Request-ID")
        if reqID == "" {
            reqID = generateTraceID() // 自动生成
            c.Header("X-Request-ID", reqID) // 响应头也带上
        }
        // 存入 context，后续处理链都能取到
        c.Set("trace_id", reqID)
        c.Next()
    }
}
```

### 1.4 Header 传递：跨服务时 ID 如何"接力"？

生成/获取到 TraceID 只是第一步，关键是**让下游服务也能拿到它**。PrivShield 在三个层面实现了传递：

#### 1.4.1 HTTP 层：请求头透传

当 BFF 调用 Service-Hub、Datasource-Mgr 等下游 HTTP 服务时，**自动将 `X-Request-ID` 和 `X-Trace-ID` 加入外发请求的 Header**：

```go
// BFF 调用 Service-Hub 时
req, _ := http.NewRequest("POST", "http://service-hub:8082/api/hub/dispatch", body)
req.Header.Set("X-Request-ID", traceID)  // 从当前 context 取出，继续传递
req.Header.Set("X-Trace-ID", traceID)
```

#### 1.4.2 gRPC 层：Metadata 透传

gRPC 不使用 HTTP Header，而是使用 **Metadata**。PrivShield 在 gRPC 客户端拦截器中自动注入：

```go
// console/bff-go/internal/agent/client.go
md := metadata.Pairs("x-request-id", traceID, "x-trace-id", traceID)
ctx = metadata.NewOutgoingContext(ctx, md)
// 再发起 gRPC 调用
```

服务端（Python Engine）则从 `invocation_metadata()` 中读取：
```python
# engine/grpc_server.py
metadata = dict(context.invocation_metadata())
trace_id = metadata.get('x-request-id', 'unknown')
```

#### 1.4.3 异步任务：持久化到数据库

当请求触发异步任务（如 Service-Hub 的 Phase B 租约 Worker），TraceID 会**存入数据库的任务记录**中：

```go
// services/service-hub/internal/handlers/handlers.go
task := &models.Task{
    TraceID: traceID,  // 持久化
    // ...
}
db.Create(task)

// Worker 消费时
func (w *Worker) Process(taskID string) {
    task := w.db.GetTask(taskID)
    ctx := context.WithValue(context.Background(), "trace_id", task.TraceID)
    // 后续所有日志、调用都带上这个 TraceID
}
```

### 1.5 完整链路示例

以一个"医保数据脱敏"请求为例，TraceID 的完整传递路径如下：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  ① 前端 React (console/web)                                                  │
│     生成 X-Request-ID: req-20260828-abc123                                   │
│     ──HTTP HTTPS:8081──▶                                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│  ② BFF-Go (console/bff-go :8081)                                            │
│     TraceMiddleware: 检测到 Header，存入 context                              │
│     日志: [trace_id=req-20260828-abc123] "收到脱敏请求"                      │
│     ──HTTP :8082──▶ 带 X-Request-ID                                         │
│     ──gRPC :50051──▶ 带 metadata x-request-id                               │
├─────────────────────────────────────────────────────────────────────────────┤
│  ③ Service-Hub (:8082)     │  ④ Engine gRPC (:50051)                        │
│     日志: [trace_id=req-20260828-abc123] "分发任务"                         │
│     任务.TraceID = req-20260828-abc123 (入库)                               │
│     ──HTTP :8083──▶        │     日志: [trace_id=req-20260828-abc123] "DP计算"│
├─────────────────────────────────────────────────────────────────────────────┤
│  ⑤ Datasource-Mgr (:8083)  │  ⑥ Audit-Log (:8084)                           │
│     日志: [trace_id=req-20260828-abc123] "查询 ds_yibao"                    │
│     ──HTTP :8084──▶        │     日志: [trace_id=req-20260828-abc123] "记录审计"│
├─────────────────────────────────────────────────────────────────────────────┤
│  ⑦ 异步 Worker (Phase B 租约)                                                │
│     从 DB 取出 task.TraceID = req-20260828-abc123                            │
│     日志: [trace_id=req-20260828-abc123] "任务执行完成"                      │
└─────────────────────────────────────────────────────────────────────────────┘
```

**结果**：无论在 Kibana/Grafana/Loki 中搜索哪个服务的日志，只要过滤 `trace_id="req-20260828-abc123"`，就能**一秒内看到这次请求在全栈的完整足迹**。

### 1.6 关键设计要点总结

| 设计点 | 说明 |
|:---|:---|
| **自动注入** | 入口中间件自动检查并补全 TraceID，不依赖前端一定传 |
| **双头下发** | `X-Request-ID` + `X-Trace-ID`，兼容业务追踪与技术追踪 |
| **协议全覆盖** | HTTP Header、gRPC Metadata、数据库持久化、异步 Context 四种载体 |
| **响应头回传** | 服务端把 TraceID 写回响应头，前端报错时可直接展示给用户/运维 |
| **日志强制携带** | Python `extra={"trace_id": ...}` 与 Go `slog` 的默认字段，确保每条日志都有 ID |
| **不丢失原则** | 即使跨越异步边界（Worker 消费），也能从数据库还原 TraceID |

## 第2章 API Key 鉴权与 Leaky Bucket 限流

### 2.1 API Key 鉴权 —— 解决"谁可以访问"

#### 2.1.1 基本原理

API Key 是一种**简单但有效的身份认证机制**。调用方在每次请求的 HTTP Header 中携带一个预分配的密钥字符串，服务端验证该密钥是否合法，决定是否放行。

```
客户端请求
  Header: X-API-Key: sk-live-abc123xyz
           ↓
    ┌─────────────┐
    │  Auth中间件  │ ──▶ 密钥匹配？── 是 ──▶ 继续处理
    └─────────────┘         │
                            否
                            ↓
                    返回 401 Unauthorized
```

#### 2.1.2 PrivShield 的实现分层

文档中显示 PrivShield 并非一刀切，而是**按服务类型差异化实现**：

| 服务类型 | 鉴权方式 | 配置项 | 说明 |
|:---|:---|:---|:---|
| **console/bff-go** | 合并式 `securityMiddleware()` | `CONSOLE_API_KEY` | 将鉴权与限流合并为单一中间件，带后台 goroutine 清理过期 IP |
| **其他 Go 微服务** | 独立 `Auth()` 中间件 | `PRIVACY_AUTH_ENABLED` + API Key | 标准中间件链中的独立鉴权环节 |
| **Python 引擎** | 可选启用 | `PRIVACY_AUTH_ENABLED` | REST/gRPC 均可启用 API Key 校验 |

**环境变量配置示例**：
```bash
# BFF 网关
CONSOLE_API_KEY="sk-privshield-console-2026"

# 通用 Go 服务
PRIVACY_AUTH_ENABLED=true

# Python 引擎
PRIVACY_AUTH_ENABLED=true
```

#### 2.1.3 鉴权流程细节

```
请求进入
  ↓
[TraceMiddleware] 注入 TraceID
  ↓
[Auth Middleware] 检查 Header
    │
    ├─ 未携带 X-API-Key ──▶ 返回 401 + 统一错误信封
    │   {
    │     "code": "AUTH_MISSING",
    │     "message": "缺少 API Key 认证头",
    │     "trace_id": "req-xxx"
    │   }
    │
    ├─ Key 不匹配 ──▶ 返回 403 + 统一错误信封
    │   {
    │     "code": "AUTH_INVALID",
    │     "message": "API Key 无效或已吊销",
    │     "trace_id": "req-xxx"
    │   }
    │
    └─ Key 有效 ──▶ 继续下游中间件
```

> **Fail-Closed 原则**：鉴权未通过时一律拒绝，不存在"降级为匿名访问"的漏洞。

### 2.2 Leaky Bucket 限流 —— 解决"访问有多快"

#### 2.2.1 基本原理

**Leaky Bucket（漏桶）**是一种流量整形算法，形象比喻如下：

```
        请求流入（可能突发）
              ↓
    ┌─────────────────┐
    │   请求队列（桶）  │  ◄── 桶有容量限制，满了就溢出（拒绝）
    │  [req][req][req]│
    └────────┬────────┘
             │ 以固定速率"漏"出处理
             ▼
        匀速处理请求
```

**核心特性**：
- **流入不限速**：允许短突发流量进入队列
- **流出匀速**：后端以固定速率处理，保护系统不被压垮
- **溢出丢弃**：当桶满时，新请求直接被拒绝（返回 429 Too Many Requests）

与 **Token Bucket（令牌桶）**的区别：
| 特性 | Leaky Bucket | Token Bucket |
|:---|:---|:---|
| 突发流量 | 缓存后匀速处理 | 允许一定突发（有令牌就能过） |
| 适用场景 | 严格限速、保护下游 | 允许弹性、平滑限流 |
| PrivShield 使用 | Go 服务默认 | `console/bff-go` 的滑动窗口限流 |

#### 2.2.2 限流配置矩阵

文档 §2.2 和 §7.2 中披露了各服务的限流参数：

| 服务 | 算法 | 配置项 | 默认值 | 说明 |
|:---|:---|:---|:---:|:---|
| **service-hub** | Leaky Bucket | `SERVICE_HUB_RATE_LIMIT_RPS` / `_BURST` | 100 / 200 | 每秒 100 请求，突发 200 |
| **datasource-mgr** | Leaky Bucket | `DATASOURCE_MGR_RATE_LIMIT_RPS` / `_BURST` | 100 / 200 | 同上 |
| **audit-log** | Leaky Bucket | 继承通用配置 | — | 审计写操作限流 |
| **app-lz/bff-go** | Leaky Bucket | `APP_LZ_RATE_LIMIT_RPS` / `_BURST` | 100 / 200 | 调度之眼限流 |
| **console/bff-go** | **滑动窗口** | `CONSOLE_RATE_LIMIT` | **600 req/min** | 合并式安全中间件，非漏桶 |

> **注意**：`console/bff-go` 是特殊设计——它面向前端用户，采用**滑动窗口限流**（Sliding Window）而非 Leaky Bucket，并配备后台 goroutine 定期清理过期 IP 条目，防止内存泄漏。

#### 2.2.3 限流触发后的响应

当请求超过限流阈值时，PrivShield 返回统一的错误信封：

```json
{
  "code": "RATE_LIMIT_EXCEEDED",
  "message": "请求过于频繁，请稍后再试",
  "detail": "limit: 100 rps, current burst: 205, retry_after: 3s",
  "trace_id": "req-1787554500-abc12345",
  "timestamp": "2026-08-28T09:59:00.123Z"
}
```

同时响应头会携带标准限流提示：
```
Retry-After: 3
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
```

### 2.3 两者的协同：安全中间件栈

在 PrivShield 的 Go 微服务中，这两个组件是**中间件链中的相邻环节**（§7.2）：

```text
TraceMiddleware → StructuredLogger → Recovery → SecurityHeaders → MaxBodySize → MaxConcurrent → [RateLimit] → CORS → [Auth]
                                                                                 ↑                ↑
                                                                           Leaky Bucket      API Key
```

**为什么先限流后鉴权？**

这是安全架构的经典设计：
1. **先限流**：即使攻击者使用无效 Key 发起海量请求，也在限流层被拦截，不会浪费 CPU 去计算哈希/查库鉴权 → **防御资源耗尽攻击**
2. **后鉴权**：通过限流的请求再进行身份校验，确保合法用户不受限流误伤

**console/bff-go 的合并式设计**：
```text
TraceMiddleware → ... → securityMiddleware() → ...
                              │
                              ├─ 限流检查（滑动窗口，600 req/min）
                              ├─ API Key 校验
                              └─ IP 条目清理（后台 goroutine）
```

将两者合并可以减少一次中间件跳转，提升网关性能，同时通过后台 goroutine 定期清理过期的 IP 限流计数器，避免内存无限增长。

### 2.4 实际场景示例

**场景 1：正常用户访问**
```
用户A 携带有效 Key，每秒发 10 个请求
  ↓
[RateLimit] 10 < 100 RPS ──▶ 通过
  ↓
[Auth] Key 有效 ──▶ 通过
  ↓
业务处理正常，全部成功
```

**场景 2：恶意刷接口**
```
攻击者 携带无效 Key，每秒发 1000 个请求
  ↓
[RateLimit] 1000 > 100 RPS ──▶ 前 200 个进入桶，后 800 个直接 429
  ↓
只有 200 个到达 [Auth] ──▶ Key 无效，返回 401
  ↓
系统资源消耗被控制在安全范围
```

**场景 3：突发合法流量**
```
医保结算高峰期，合法用户并发突增至 300 req/s
  ↓
[RateLimit] 桶容量 200，先处理 200 个，其余排队
  ↓
以 100 req/s 匀速处理，3 秒内消化完毕
  ↓
无服务崩溃，无数据丢失
```

### 2.5 关键设计要点总结

| 设计点 | 说明 |
|:---|:---|
| **分层鉴权** | BFF 合并式鉴权限流 vs 微服务独立中间件，按需选择 |
| **Fail-Closed** | 无 Key / 错误 Key / 超限时一律拒绝，不存在降级漏洞 |
| **统一错误信封** | 鉴权失败和限流触发均返回 `{code, message, detail, trace_id}` 标准格式 |
| **环境变量驱动** | 所有参数通过环境变量配置，支持生产动态调整 |
| **RPS=0 可关闭** | `SERVICE_HUB_RATE_LIMIT_RPS=0` 时跳过限流，便于内部测试 |
| **内存安全** | BFF 的后台 goroutine 定期清理过期 IP，防止限流计数器内存泄漏 |
| **响应头标准化** | 限流时返回 `Retry-After` 和 `X-RateLimit-*` 头，便于客户端退避 |

## 第3章 统一 JSON 响应信封包裹器

### 3.1 什么是"响应信封"？

**信封（Envelope）** 是一种 API 设计模式：无论业务数据是什么，响应体都包裹在一个**统一的外壳**中，外壳包含元信息（状态、错误、追踪等），业务数据放在内部。

```
传统方式（裸返回）：
POST /v1/privacy/mask
──▶ 200 OK
{
  "masked_value": "138****8888"
}

──▶ 400 错误
{
  "error": "invalid field name"
}
─────────────────────────────────
问题：成功和失败的结构完全不同，前端需要写两套解析逻辑
```

```
信封方式（统一外壳）：
POST /v1/privacy/mask
──▶ 200 OK
{
  "code": "SUCCESS",
  "message": "脱敏完成",
  "detail": { "masked_value": "138****8888" },
  "trace_id": "req-abc123",
  "timestamp": "2026-08-28T10:01:00Z"
}

──▶ 400 错误
{
  "code": "INVALID_FIELD_NAME",
  "message": "字段名无效",
  "detail": "field 'phonee' is not registered",
  "trace_id": "req-abc123",
  "timestamp": "2026-08-28T10:01:00Z"
}
─────────────────────────────────
优势：成功/失败结构完全一致，前端只需一个解析函数
```

### 3.2 PrivShield 的统一信封格式

全栈（Python + Go + 前端双控制台）强制遵循以下标准结构：

```json
{
  "code": "INVALID_DATASOURCE_ID",
  "message": "指定的业务数据源不存在或未激活",
  "detail": "datasource 'ds_unknown' is not registered in canonical naming",
  "trace_id": "req-1787554500-abc12345",
  "timestamp": "2026-08-27T09:30:00.123Z"
}
```

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| **`code`** | string | **机器可读的错误码**。如 `SUCCESS`、`INVALID_DATASOURCE_ID`、`RATE_LIMIT_EXCEEDED`。用于前端做条件判断（如 `if code === 'BUDGET_EXHAUSTED' 则显示充值提示`） |
| **`message`** | string | **人类可读的错误摘要**。面向终端用户的友好提示，可直接展示在 UI 上 |
| **`detail`** | string/object | **调试详情**。面向开发者的技术细节，可能包含堆栈、参数说明等。生产环境可配置脱敏 |
| **`trace_id`** | string | **追踪 ID**。与 `X-Request-ID` 一致，用户报错时把这个 ID 给运维，可一秒定位全链路日志 |
| **`timestamp`** | ISO8601 | **服务端时间戳**。用于排查时钟偏差、缓存失效、时序问题 |

### 3.3 双端实现：Python 与 Go 如何统一？

#### 3.3.1 Python 端（FastAPI 全局异常拦截）

文件：`engine/observability/envelope.py`

```python
# 核心思想：注册全局异常处理器，捕获所有异常后统一包装
@app.exception_handler(RequestValidationError)
@app.exception_handler(HTTPException)
@app.exception_handler(Exception)  # 兜底未捕获异常
async def envelope_handler(request, exc):

    # 从请求上下文中取出 TraceID（由中间件注入）
    trace_id = request.state.trace_id or generate_trace_id()

    # 将异常映射为标准信封
    envelope = {
        "code": map_exception_to_code(exc),      # 如 "VALIDATION_ERROR"
        "message": get_user_message(exc),         # 如 "请求参数格式不正确"
        "detail": get_debug_detail(exc),          # 如 "field 'epsilon' must be > 0"
        "trace_id": trace_id,
        "timestamp": datetime.utcnow().isoformat() + "Z"
    }

    # 返回统一格式，HTTP 状态码仍按语义设置（400/401/429/500）
    return JSONResponse(
        status_code=map_to_http_status(exc),
        content=envelope
    )
```

**覆盖的异常类型**：
- `RequestValidationError`（Pydantic 参数校验失败）→ 400
- `HTTPException`（业务主动抛错）→ 按指定状态码
- `PrivacyBudgetExhaustedError` → 429
- 未捕获异常 → 500（兜底，避免暴露敏感信息）

#### 3.3.2 Go 端（Gin 中间件统一响应函数）

文件：`pkg/middleware/envelope.go`

```go
// 所有 Go 微服务统一调用的响应函数
func AbortWithError(c *gin.Context, httpStatus int, code, message, detail string) {

    // 从 Gin context 中取出 TraceID（由 TraceMiddleware 注入）
    traceID, _ := c.Get("trace_id")
    if traceID == "" {
        traceID = generateTraceID()
    }

    envelope := gin.H{
        "code":      code,        // 如 "INVALID_DATASOURCE_ID"
        "message":   message,     // 如 "数据源不存在"
        "detail":    detail,      // 如 "ds_unknown not found"
        "trace_id":  traceID,
        "timestamp": time.Now().UTC().Format(time.RFC3339Nano),
    }

    // 终止后续处理链，直接返回信封
    c.AbortWithStatusJSON(httpStatus, envelope)
}
```

**使用示例**（在 Handler 中）：
```go
func GetDatasource(c *gin.Context) {
    id := c.Param("id")

    ds, err := store.FindDatasource(id)
    if err != nil {
        // 统一调用，不再各自拼 JSON
        AbortWithError(c, 400, "INVALID_DATASOURCE_ID", 
            "指定的业务数据源不存在或未激活",
            fmt.Sprintf("datasource '%s' is not registered", id))
        return
    }

    // 成功时也走信封（data 字段放业务数据）
    c.JSON(200, gin.H{
        "code": "SUCCESS",
        "message": "查询成功",
        "detail": ds,  // 业务数据放在 detail 或新增 data 字段
        "trace_id": c.GetString("trace_id"),
        "timestamp": time.Now().UTC().Format(time.RFC3339Nano),
    })
}
```

### 3.4 前端双控制台如何解析？

文件：`console/web/src/api/client.ts` 和 `console/app-lz/web/src/api/client.ts`

```typescript
// 统一的 Axios 响应拦截器
apiClient.interceptors.response.use(
    (response) => {
        // 成功响应：直接返回业务数据，剥离信封外壳
        if (response.data?.code === 'SUCCESS') {
            return response.data.detail ?? response.data;
        }
        // 异常情况（HTTP 200 但业务码非 SUCCESS）
        return Promise.reject(normalizeError(response.data));
    },
    (error) => {
        // HTTP 错误（4xx/5xx）：统一解析信封
        const envelope = error.response?.data;

        // 向后兼容：旧系统可能返回 {error: "..."} 格式
        const normalized = {
            code: envelope?.code || 'UNKNOWN_ERROR',
            message: envelope?.message || envelope?.error || '请求失败',
            detail: envelope?.detail || '',
            trace_id: envelope?.trace_id || error.response?.headers['x-request-id'] || 'unknown',
            timestamp: envelope?.timestamp || new Date().toISOString()
        };

        // 自动上报或展示
        notification.error({
            message: normalized.message,
            description: `${normalized.detail} [TraceID: ${normalized.trace_id}]`,
        });

        return Promise.reject(normalized);
    }
);
```

**关键设计**：
- **向后兼容**：如果后端返回旧格式 `{error: "..."}`，前端自动映射到新的 `code`/`message` 字段
- **TraceID 回退**：如果响应体里没有 `trace_id`，从响应头 `X-Request-ID` 取
- **统一 UI 提示**：所有错误都经过同一套通知组件，用户看到的风格一致

### 3.5 为什么需要"包裹器"（Middleware）而非手动拼？

| 方式 | 问题 | 包裹器方式的优势 |
|:---|:---|:---|
| **各 Handler 手动写 JSON** | 格式不统一，有人写 `error`，有人写 `msg`，有人忘带 `trace_id` | 强制收敛，一处定义，全局生效 |
| **业务代码里 try-catch 包装** | 容易遗漏，未捕获异常直接暴露堆栈 | 全局异常处理器兜底，500 错误也走信封 |
| **前后端各自约定** | 改格式需要改 N 个文件，容易漏 | 改 `envelope.py` 和 `envelope.go` 两处即可 |
| **跨语言项目** | Python 和 Go 的异常模型不同，格式更难对齐 | 双端分别实现同一接口契约，前端无感知 |

### 3.6 平滑迁移与过渡期设计

文档强调这是一个**已完成（✅）的迁移专项**，过渡期采取了以下兼容措施：

```
┌─────────────────────────────────────────────────────────────┐
│  过渡期兼容策略                                              │
├─────────────────────────────────────────────────────────────┤
│  1. 响应头强制下发双追踪头                                    │
│     X-Request-ID: req-abc123                                 │

│  2. 保留 detail 字段                                          │
│     旧客户端可能依赖 detail 获取错误信息，新信封仍保留该字段     │

├─────────────────────────────────────────────────────────────┤
│  3. 前端双控制台统一解析                                      │
│     console/web 和 console/app-lz/web 共用同一套 client.ts    │

├─────────────────────────────────────────────────────────────┤

└─────────────────────────────────────────────────────────────┘
```

### 3.7 一句话总结

> **统一 JSON 响应信封包裹器 = 给所有 API 响应（无论成功/失败、无论 Python/Go）套上一个标准外壳，让前端用同一套逻辑解析，让运维用同一个 TraceID 追踪，让开发者用同一个错误码定位问题。**

## 第4章 DDoS 防护 (MaxBodySize/MaxConcurrent/RateLimit)

### 4.1 为什么需要三层？单一防护不够吗？

DDoS（分布式拒绝服务）攻击有多种形态，单一防护无法覆盖：

| 攻击类型 | 特征 | 单靠 RateLimit 能防吗？ |
|:---|:---|:---|
| **大文件轰炸** | 上传 10GB 垃圾文件撑爆内存 | ❌ 速率正常，但体积极大 |
| **慢速连接耗尽** | 开 10 万个连接，每个每秒发 1 字节 | ❌ 速率极低，但连接数爆炸 |
| **高频请求冲刷** | 单 IP 每秒 10 万次正常小请求 | ✅ 可以防 |
| **混合攻击** | 上述多种组合 | ❌ 必须多层联防 |

**PrivShield 的三层设计**：

```
请求进入
  │
  ├──▶ 第一层：MaxBodySize ──▶ 拦截"大体积"攻击
  │
  ├──▶ 第二层：MaxConcurrent ──▶ 拦截"连接耗尽"攻击
  │
  └──▶ 第三层：RateLimit ──▶ 拦截"高频冲刷"攻击
            │
            ▼
        到达业务逻辑
```

### 4.2 第一层：MaxBodySize —— 限制请求体大小

#### 4.2.1 解决什么问题？

防止攻击者通过上传**超大请求体**导致：
- 内存溢出（OOM）
- 磁盘写满
- JSON/Protobuf 解析器 CPU 占满

#### 4.2.2 实现方式

Go 中间件在读取 Body 前检查 `Content-Length`：

```go
// pkg/middleware/ddos.go (示意)
func MaxBodySize(maxBytes int64) gin.HandlerFunc {
    return func(c *gin.Context) {
        if c.Request.ContentLength > maxBytes {
            AbortWithError(c, 413, "PAYLOAD_TOO_LARGE",
                "请求体超过大小限制",
                fmt.Sprintf("max allowed: %d bytes, got: %d", maxBytes, c.Request.ContentLength))
            return
        }
        // 同时限制实际读取的字节数，防止 Content-Length 伪造
        c.Request.Body = http.MaxBytesReader(c.Writer, c.Request.Body, maxBytes)
        c.Next()
    }
}
```

#### 4.2.3 配置

| 服务 | 默认值 | 说明 |
|:---|:---:|:---|
| 通用 Go 服务 | **32 MB** | 常规 API 调用足够 |
| `console/bff-go` | **64 MB** | 更大，支持文件上传场景（CSV/Excel 隐私处理） |
| Python 引擎 | `PRIVACY_LIMIT_MAX_REQUESTS` 控制 | Uvicorn 层限制 |

**错误响应示例**：
```json
{
  "code": "PAYLOAD_TOO_LARGE",
  "message": "请求体超过大小限制",
  "detail": "max allowed: 33554432 bytes (32MB), got: 1073741824 bytes (1GB)",
  "trace_id": "req-xxx",
  "timestamp": "2026-08-28T10:05:00Z"
}
```

### 4.3 第二层：MaxConcurrent —— 限制在途请求总数

#### 4.3.1 解决什么问题？

防止攻击者通过**海量并发连接**（即使每个请求都很小、很慢）耗尽：
- 文件描述符（FD）
- 线程/协程池
- 数据库连接池
- 内存（每个连接都占缓冲）

这就是经典的 **Slowloris 攻击** 原理：开大量连接，每个都拖得很慢，服务器资源被占满，正常用户连不进来。

#### 4.3.2 实现方式

使用**信号量（Semaphore）**控制同时处理的请求数：

```go
// pkg/middleware/ddos.go (示意)
func MaxConcurrent(limit int) gin.HandlerFunc {
    sem := make(chan struct{}, limit) // 容量为 limit 的信号量通道

    return func(c *gin.Context) {
        select {
        case sem <- struct{}{}: // 获取许可
            defer func() { <-sem }() // 请求结束后释放
            c.Next()
        default: // 信号量已满
            AbortWithError(c, 503, "SERVICE_OVERLOADED",
                "服务器并发请求过多，请稍后再试",
                fmt.Sprintf("concurrent limit: %d", limit))
        }
    }
}
```

#### 4.3.3 配置

| 服务 | 默认值 | 说明 |
|:---|:---:|:---|
| 通用 Go 服务 | **1000** | 在途请求超过 1000 时新请求直接 503 |
| Python 引擎 | `PRIVACY_LIMIT_CONCURRENCY` = 10000 | Uvicorn 层控制最大并发连接 |

**关键行为**：
- **不排队**：超过上限直接拒绝（503），避免队列堆积拖垮系统
- **快速失败**：让客户端立即知道，而不是无限等待
- **与连接池协同**：这个限制通常略小于数据库连接池上限，保护底层存储

### 4.4 第三层：RateLimit —— 限制请求速率

#### 4.4.1 解决什么问题？

防止单客户端（单 IP 或单用户）在**单位时间内发送过多请求**：
- API 滥用（爬虫、暴力破解）
- 刷接口消耗隐私预算
- 高频查询拖慢数据库

#### 4.4.2 实现方式：Token Bucket（令牌桶）

文档中 Go 通用服务使用 **Token Bucket**（与 BFF 的 Leaky Bucket 不同）：

```
令牌以固定速率（RPS）放入桶中
桶有最大容量（Burst）
每个请求需要消耗 1 个令牌
桶空时，请求被拒绝（429）
```

```go
// 基于 golang.org/x/time/rate
func RateLimit(rps float64, burst int) gin.HandlerFunc {
    limiter := rate.NewLimiter(rate.Limit(rps), burst)

    return func(c *gin.Context) {
        if !limiter.Allow() {
            AbortWithError(c, 429, "RATE_LIMIT_EXCEEDED",
                "请求过于频繁，请稍后再试",
                fmt.Sprintf("limit: %.0f rps, burst: %d", rps, burst))
            return
        }
        c.Next()
    }
}
```

#### 4.4.3 配置

| 服务 | RPS | Burst | 说明 |
|:---|:---:|:---:|:---|
| `service-hub` | 100 | 200 | 调度中枢，控制任务分发速率 |
| `datasource-mgr` | 100 | 200 | 数据源管理，防止数据库被刷 |
| `audit-log` | 100 | 200 | 审计写入，保护 PG 写入性能 |
| `app-lz/bff-go` | 100 | 200 | 调度之眼控制台 |
| `console/bff-go` | — | — | 使用独立滑动窗口（600 req/min） |

**关闭方式**：设置 `*_RATE_LIMIT_RPS=0` 时跳过该中间件（内部测试用）。

### 4.5 完整中间件栈顺序

文档 §7.2 中规定的**严格顺序**至关重要：

```text
TraceMiddleware → StructuredLogger → Recovery → SecurityHeaders → MaxBodySize → MaxConcurrent → [RateLimit] → CORS → Auth
                      ↑                                               ↑              ↑           ↑
                    记录日志                                        先拦大文件    再拦连接耗尽   最后限速率
```

**为什么是这个顺序？**

| 顺序 | 理由 |
|:---|:---|
| **MaxBodySize 在最前** | 如果请求体有 10GB，越早拒绝越好，避免后续中间件浪费资源去解析 |
| **MaxConcurrent 次之** | 连接数限制比速率限制更底层，防止连接层面的资源耗尽 |
| **RateLimit 在后** | 通过前两层的请求才进入速率判断，减少限流计数器的无效更新 |
| **Auth 在最后** | 先挡掉"明显恶意"的流量，再对"可能合法"的流量做鉴权计算（省 CPU） |

> **例外**：`console/bff-go` 使用合并式 `securityMiddleware()`，将 RateLimit + Auth 合并，并带 IP 清理机制。

### 4.6 Python 引擎的对应防护

Python 引擎（FastAPI/Uvicorn）不经过 Go 中间件栈，但在框架层实现了对等防护：

| 机制 | 环境变量 | 默认值 | 对应 Go 层 |
|:---|:---|:---:|:---|
| 并发连接限制 | `PRIVACY_LIMIT_CONCURRENCY` | 10000 | MaxConcurrent |
| 单连接请求上限 | `PRIVACY_LIMIT_MAX_REQUESTS` | 100000 | 防内存泄漏 |
| 空闲连接超时 | `PRIVACY_TIMEOUT_KEEP_ALIVE` | 30 秒 | 清理僵尸连接 |
| gRPC 限流 | `RateLimitInterceptor` | 按路径配置 | RateLimit |

**差异说明**：
- Python 层的并发限制（10000）远高于 Go 层（1000），因为 Python 引擎通常部署在内部，由 Gateway/BFF 前置过滤
- gRPC 有独立的拦截器级限流，与 HTTP 层的限制策略分开配置

### 4.7 三层协同的防御效果

```
攻击场景：10 万台肉鸡，每台每秒发 100 个请求，部分携带 100MB 文件

                正常流量        恶意流量
                    │              │
  MaxBodySize      ─┼─▶ 通过      ├──▶ 413 拒绝 (大文件)
                    │              │
  MaxConcurrent    ─┼─▶ 通过      ├──▶ 503 拒绝 (连接占满)
                    │              │
  RateLimit        ─┼─▶ 通过      ├──▶ 429 拒绝 (超频)
                    │              │
                    ▼              ▼
                 业务处理      几乎无法穿透
```

### 4.8 一句话总结

> **MaxBodySize 防"胖请求"，MaxConcurrent 防"连接海"，RateLimit 防"高频刷"——三层纵深防御，确保无论攻击者从哪个维度施压，PrivShield 都能在到达业务逻辑前将其拦截，同时保证正常用户的请求畅通无阻。**

## 第5章 安全响应头 (CSP/HSTS/X-Frame-Options)

### 5.1 概述

这是 PrivShield **统一中间件与上下文透传层**中的**浏览器安全加固**机制。这些响应头由服务端通过 HTTP Header 下发给浏览器，**告诉浏览器"这个页面允许做什么、不允许做什么"**，从而阻断多种常见的 Web 攻击向量。

> 关键特点：**不依赖代码漏洞修复**，纯配置层面的防御，成本低、效果好。

### 5.2 PrivShield 注入的四个安全头

文档 §7.2 披露，Go 微服务统一通过 `SecurityHeaders()` 中间件注入以下响应头：

| 响应头 | 全称 | 防御目标 |
|:---|:---|:---|
| **`CSP`** | Content Security Policy | XSS、数据注入、恶意脚本执行 |
| **`HSTS`** | HTTP Strict Transport Security | SSL 剥离、中间人攻击 |
| **`X-Frame-Options`** | — | 点击劫持（Clickjacking） |
| **`X-Content-Type-Options`** | — | MIME 类型嗅探攻击 |

### 5.3 CSP —— 内容安全策略

#### 5.3.1 解决什么问题？

**XSS（跨站脚本攻击）** 和 **数据注入攻击**。攻击者在页面中插入恶意脚本（如 `<script>窃取cookie</script>`），浏览器会无条件执行。

#### 5.3.2 原理

CSP 是一个**白名单策略**：服务端声明"只允许从哪些来源加载脚本、样式、图片等资源"，浏览器严格执行，违反则拦截并上报。

```
┌─────────────────────────────────────────────┐
│  攻击者注入恶意脚本                           │
│  <script src="https://evil.com/steal.js">   │
│              ↓                              │
│  浏览器收到 CSP: script-src 'self'          │
│              ↓                              │
│  "evil.com 不在白名单内" ──▶ 拒绝加载并告警   │
└─────────────────────────────────────────────┘
```

#### 5.3.3 典型配置

```http
Content-Security-Policy: 
  default-src 'self';
  script-src 'self' 'unsafe-inline';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data:;
  connect-src 'self' https://api.privshield.internal;
  frame-ancestors 'none';
  report-uri /api/csp-report
```

| 指令 | 含义 |
|:---|:---|
| `default-src 'self'` | 默认只允许同源资源 |
| `script-src 'self'` | JS 只能从本站加载，阻断外部恶意脚本 |
| `frame-ancestors 'none'` | 禁止任何页面嵌入本站（与 X-Frame-Options 协同） |
| `report-uri` | 违规时自动上报到服务端，便于发现攻击 |

> **注意**：`'unsafe-inline'` 允许内联脚本/样式，是因为前端 React/Vite 构建产物可能需要。生产环境如使用 nonce 或 hash 可进一步收紧。

### 5.4 HSTS —— HTTP 严格传输安全

#### 5.4.1 解决什么问题？

**SSL 剥离攻击（SSL Stripping）**。攻击者拦截用户流量，强制降级到不安全的 HTTP，从而窃取明文传输的敏感数据（如 API Key、隐私数据）。

```
正常流程：用户输入 http:// ──▶ 301 跳转 https:// ──▶ 安全传输
                ↑
攻击者拦截：    http://（明文）◄────── 用户无感知，数据被窃听
```

#### 5.4.2 原理

HSTS 告诉浏览器：**"这个域名在未来 N 秒内，只允许通过 HTTPS 访问，不要接受任何 HTTP 请求，也不要让用户点击证书警告继续访问。"**

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

| 参数 | 含义 |
|:---|:---|
| `max-age=31536000` | 记住 1 年（秒），期间强制 HTTPS |
| `includeSubDomains` | 对 *.privshield.internal 所有子域生效 |
| `preload` | 申请加入浏览器内置预加载列表，首次访问即生效 |

**效果**：
- 用户即使手动输入 `http://`，浏览器也会**内部自动改写为 `https://`**，不发送任何明文请求
- 遇到无效/自签名证书时，**禁止用户点击"继续访问"绕过**

### 5.5 X-Frame-Options —— 点击劫持防护

#### 5.5.1 解决什么问题？

**点击劫持（Clickjacking）**。攻击者用一个透明的 `<iframe>` 将 PrivShield 控制台嵌入恶意页面，诱导用户在不知情的情况下点击"删除数据""导出隐私报告"等按钮。

```
┌─────────────────────────────────────────────┐
│  恶意页面（外观：抽奖按钮）                    │
│  ┌─────────────────────────────────────┐   │
│  │  [点击抽奖]  ← 实际点击的是下面的 iframe │
│  │  ╔═════════════════════════════════╗ │   │
│  │  ║  PrivShield 控制台（透明不可见） ║ │   │
│  │  ║  [确认删除所有审计日志]          ║ │   │
│  │  ╚═════════════════════════════════╝ │   │
│  └─────────────────────────────────────┘   │
└─────────────────────────────────────────────┘
```

#### 5.5.2 原理

禁止浏览器将本站页面嵌入到 `<iframe>`、`<frame>`、`<object>` 中。

```http
X-Frame-Options: DENY
```

| 取值 | 含义 |
|:---|:---|
| `DENY` | **完全禁止**嵌入（PrivShield 采用此策略） |
| `SAMEORIGIN` | 仅允许同源嵌入 |
| `ALLOW-FROM uri` | 允许指定域名嵌入（已废弃，现代浏览器不支持） |

> **与 CSP 的 `frame-ancestors` 协同**：`X-Frame-Options` 是旧标准，CSP 的 `frame-ancestors` 是更现代、更灵活的替代。PrivShield 两者同时下发，确保兼容所有浏览器。

### 5.6 X-Content-Type-Options —— MIME 嗅探防护

#### 5.6.1 解决什么问题？

**MIME 类型嗅探攻击**。某些浏览器会"智能猜测"文件类型（如将用户上传的 `.jpg` 识别为可执行脚本），攻击者利用此特性上传伪装文件执行恶意代码。

#### 5.6.2 原理

强制浏览器**严格使用服务端声明的 Content-Type**，禁止猜测。

```http
X-Content-Type-Options: nosniff
```

**典型攻击场景被阻断**：
```
攻击者上传文件名为 report.html 但 Content-Type 设为 image/jpeg
        ↓
浏览器收到 nosniff ──▶ "我不猜，你说这是图片我就按图片显示"
        ↓
report.html 中的 <script> 不会被执行
```

### 5.7 实现与中间件栈位置

文档 §7.2 指出，Go 微服务通过 `SecurityHeaders()` 中间件**统一注入**，值为固定配置：

```go
// pkg/middleware/security.go (示意)
func SecurityHeaders() gin.HandlerFunc {
    return func(c *gin.Context) {
        // 内容安全策略
        c.Header("Content-Security-Policy", 
            "default-src 'self'; script-src 'self'; style-src 'self'; frame-ancestors 'none'")

        // 强制 HTTPS
        c.Header("Strict-Transport-Security", 
            "max-age=31536000; includeSubDomains; preload")

        // 禁止嵌入
        c.Header("X-Frame-Options", "DENY")

        // 禁止 MIME 嗅探
        c.Header("X-Content-Type-Options", "nosniff")

        c.Next()
    }
}
```

**在中间件栈中的位置**：
```text
TraceMiddleware → StructuredLogger → Recovery → SecurityHeaders → MaxBodySize → ...
                                                    ↑
                                              尽早注入，确保所有响应（包括错误响应）都带安全头
```

**为什么放在 Recovery 之后？**
- `Recovery` 中间件捕获 panic 后返回 500 错误
- `SecurityHeaders` 紧随其后，确保**即使是异常响应**，浏览器也能收到安全策略
- 如果放在最后，panic 导致的提前返回会漏掉安全头

### 5.8 四者协同的防御矩阵

| 攻击类型 | 无安全头 | 有 CSP | 有 HSTS | 有 X-Frame-Options | 有 X-Content-Type-Options |
|:---|:---:|:---:|:---:|:---:|:---:|
| XSS 脚本注入 | ✅ 中招 | ❌ 阻断 | — | — | — |
| 外部恶意脚本加载 | ✅ 中招 | ❌ 阻断 | — | — | — |
| SSL 降级窃听 | ✅ 中招 | — | ❌ 阻断 | — | — |
| 点击劫持 | ✅ 中招 | ❌ 阻断 | — | ❌ 阻断 | — |
| MIME 嗅探执行 | ✅ 中招 | — | — | — | ❌ 阻断 |

> ✅ = 存在漏洞，❌ = 被阻断，— = 不相关

### 5.9 验收与验证

部署后可通过 curl 验证：

```bash
curl -I https://console.privshield.internal/api/health

HTTP/2 200
content-security-policy: default-src 'self'; ...
strict-transport-security: max-age=31536000; includeSubDomains; preload
x-frame-options: DENY
x-content-type-options: nosniff
x-request-id: req-abc123
```

或使用浏览器 DevTools → Network → 点击任意请求 → Response Headers 查看。

### 5.10 一句话总结

> **CSP 告诉浏览器"只能执行我允许的脚本"，HSTS 告诉浏览器"永远用 HTTPS 访问我"，X-Frame-Options 告诉浏览器"不要把我嵌入到别人的页面里"，X-Content-Type-Options 告诉浏览器"我说是什么类型就是什么类型"——四道响应头指令，在浏览器层面筑起最后一道安全防线，即使应用层代码存在漏洞，也能大幅降低攻击成功率。**

## 第6章 全栈可观测性体系 (Observability)

### 6.1 概述

这是 PrivShield **第 6 章**的核心设计，解决的是**"系统出问题时，如何快速定位根因；系统正常运行时，如何提前发现风险"**的问题。

> **可观测性（Observability）** 不是简单的"监控"，而是通过系统**外部输出**（指标、日志、追踪）推断其**内部状态**的能力。类比：通过汽车仪表盘（速度、油量、水温）判断发动机是否健康。

### 6.2 三大支柱

业界经典的 **Observability 三大支柱**，PrivShield 全部覆盖：

```
┌─────────────────────────────────────────────────────────────┐
│                    全栈可观测性体系                           │
├─────────────────┬─────────────────┬─────────────────────────┤
│    Metrics      │      Logs       │       Traces            │
│    (指标)        │    (日志)        │      (追踪)             │
├─────────────────┼─────────────────┼─────────────────────────┤
│  "系统出了什么   │  "系统说了什么"  │  "请求走过了哪里"        │
│   问题？"        │                 │                         │
├─────────────────┼─────────────────┼─────────────────────────┤
│  Prometheus     │  JSON/Text      │  OpenTelemetry          │
│  计数器/直方图   │  结构化日志      │  分布式追踪              │
│  仪表盘/告警     │  全链路关联      │  跨服务调用链            │
└─────────────────┴─────────────────┴─────────────────────────┘
                    ↓
              Grafana 统一可视化
```

### 6.3 Prometheus 指标体系 —— "系统出了什么问题？"

#### 6.3.1 设计哲学

**指标是聚合的、可计算的、适合告警的**。比如"过去 5 分钟内脱敏接口的 P99 延迟是否超过 2 秒"——这是一个适合用指标回答的问题。

#### 6.3.2 Python 引擎端（40 个指标）

文件：`engine/observability/metrics.py`

按业务域分类：

**核心隐私原语指标**（Counter + Histogram 成对出现）：
| 指标名 | 类型 | 用途 |
|:---|:---|:---|
| `privacy_requests_total` | Counter | REST/gRPC 请求计数（按 method/path/status） |
| `privacy_request_duration_seconds` | Histogram | 请求延迟分布，自动计算 P50/P95/P99 |
| `privacy_dp_queries_total` | Counter | 差分隐私查询次数 |
| `privacy_dp_duration_seconds` | Histogram | DP 操作耗时 |
| `privacy_masking_operations_total` | Counter | 脱敏操作次数 |
| `privacy_kano_operations_total` | Counter | K-匿名操作次数 |
| `privacy_qol_operations_total` | Counter | 查询混淆次数 |

**隐私预算指标**：
| 指标名 | 类型 | 用途 |
|:---|:---|:---|
| `privacy_budget_remaining` | **Gauge** | 实时显示各命名空间剩余 ε/δ 预算 |

> Gauge 与 Counter 的区别：Counter 只增不减（如请求数），Gauge 可增可减（如剩余预算、当前温度）。

**动态分类漏斗指标**：
| 指标名 | 类型 | 用途 |
|:---|:---|:---|
| `privacy_classification_total` | Counter | 各层（Rule/NER/LLM）分类结果统计 |
| `privacy_classification_llm_duration_seconds` | Histogram | LLM 推理延迟 |
| `privacy_classification_llm_tokens_total` | Counter | Token 消耗量（成本核算） |
| `privacy_classification_ner_total` | Counter | NER 命中/失败统计 |

**网关指标**：
| 指标名 | 类型 | 用途 |
|:---|:---|:---|
| `privacy_gateway_healthy_nodes` | Gauge | 健康后端节点数（=0 时触发 P0 告警） |
| `privacy_gateway_circuit_breaker_state` | Gauge | 熔断器状态（0=Closed, 1=Open, 2=Half-Open） |

#### 6.3.3 Go 微服务端（15+ 指标）

文件：`pkg/metrics/metrics.go`

| 指标名 | 类型 | 用途 |
|:---|:---|:---|
| `http_requests_total` | Counter | HTTP 请求计数 |
| `http_request_duration_seconds` | Histogram | HTTP 延迟 |
| `agent_requests_total` | Counter | gRPC 调用 Engine 次数 |

### 6.4 结构化日志规范 —— "系统说了什么？"

#### 6.4.1 设计哲学

**日志是离散的、详细的、适合审计的**。比如"2026-08-28 10:15:23，用户 admin 对 ds_yibao 执行了 mask 操作，消耗 ε=0.1，TraceID=req-abc123"——这是日志该记录的内容。

#### 6.4.2 Python 引擎

### 6.5 OpenTelemetry 分布式追踪 —— "请求走过了哪里？"

#### 6.5.1 设计哲学

**追踪是请求级的、跨服务的、适合定位延迟瓶颈的**。比如"为什么这个脱敏请求花了 5 秒？是 BFF 慢了、Hub 慢了、还是 Engine 的 LLM 推理卡住了？"——只有追踪能回答。

#### 6.5.2 架构

```
┌──────────────┐     HTTP/X-Request-ID      ┌──────────────┐
│   前端 React  │ ─────────────────────────▶ │  BFF-Go      │
└──────────────┘                            └──────┬───────┘
                                                   │
                          gRPC Metadata/x-request-id
                                                   ▼
┌──────────────┐     HTTP/X-Request-ID      ┌──────────────┐
│  Audit-Log   │ ◀───────────────────────── │ Service-Hub  │
└──────────────┘                            └──────┬───────┘
                                                   │
                                                   ▼
                                            ┌──────────────┐
                                            │ Python Engine│
                                            │ (SpanExport) │
                                            └──────┬───────┘
                                                   │
                                              OTLP/gRPC
                                                   ▼
                                            ┌──────────────┐
                                            │Jaeger/Tempo  │
                                            │(Trace Backend)│
                                            └──────────────┘
```

#### 6.5.3 Python 引擎的 OTel 集成

文件：`engine/observability/tracing.py`

```python
# 通过环境变量激活
OTEL_EXPORTER_OTLP_ENDPOINT="http://jaeger:4317"

# 未设置时自动降级为 no-op（零开销）
```

**特性**：
- `BatchSpanProcessor`：批量导出，减少网络开销
- Span 自动关联 `X-Request-ID`，与 Go 端 TraceMiddleware 形成完整调用链
- 支持自动 instrumentation（FastAPI、gRPC、HTTP 客户端）

#### 6.5.4 追踪与日志/指标的关联

这是 PrivShield 设计的精妙之处——**三者通过 TraceID 贯通**：

```
TraceID: req-1787554500-abc12345
    │
    ├──▶ 日志中：{"trace_id": "req-...", "msg": "mask started"}
    │
    ├──▶ 指标中：privacy_requests_total{trace_id="req-..."} 
    │           （通过 exemplar 关联，高级用法）
    │
    └──▶ 追踪中：Span { trace_id: "req-...", span_id: "...", duration: 1.2s }
```

**查询场景**：
1. 用户反馈"10:15 的脱敏请求报错"
2. 从日志中搜 `trace_id=req-abc123` 找到错误详情
3. 在 Jaeger 中输入同一个 TraceID，看到跨服务调用瀑布图
4. 发现耗时集中在 `engine:LLMInference` Span（2.3s）
5. 查看 `privacy_classification_llm_duration_seconds` 指标，确认 LLM 延迟突增
6. 根因：GPU 节点负载过高

### 6.6 Grafana 仪表盘与告警

#### 6.6.1 预置仪表盘

文件：
- `deploy/grafana/dashboard.json` —— 全栈总览
- `deploy/grafana/service-hub-dashboard.json` —— 调度中枢专项

**典型面板**：
- QPS / 延迟热力图（按接口维度下钻）
- 隐私预算消耗趋势（按命名空间）
- 分类漏斗各层转化率（Rule → NER → LLM）
- 熔断器状态图（红/黄/绿）
- 后端节点健康状态

#### 6.6.2 推荐告警规则

| 告警条件 | 等级 | 含义 |
|:---|:---:|:---|
| `privacy_requests_total{status=~"5.."}` 5min rate 突增 | **P1** | 服务端错误激增，可能代码 Bug 或依赖故障 |
| `privacy_gateway_healthy_nodes == 0` | **P0** | 所有后端 Engine 不可用，服务完全中断 |
| `circuit_breaker_state > 0` 持续 5min | **P2** | 后端持续异常，进入熔断保护状态 |
| `privacy_budget_remaining < 0.1` | **P1** | 隐私预算即将耗尽，需扩容或等待重置 |
| `task_lease_conflicts_total` 5min rate > 100 | **P2** | 租约争抢严重，Worker 配置可能不当 |

```
┌─────────────────────────────────────────────────────────────┐
│                        用户请求                              │
└─────────────────────────────────────────────────────────────┘
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
   ┌─────────┐       ┌──────────┐        ┌──────────┐
   │ Metrics │       │   Logs   │        │  Traces  │
   │ (Prom.) │       │(JSON/Text│        │ (OTel)   │
   └────┬────┘       └────┬─────┘        └────┬─────┘
        │                 │                   │
        └─────────────────┼───────────────────┘
                          ▼
                   ┌──────────────┐
                   │   Grafana    │
                   │  (可视化)     │
                   └──────────────┘
                          │
                    ┌─────┴─────┐
                    ▼           ▼
               仪表盘展示     告警通知
               (趋势分析)     (P0/P1/P2)
```

**协同示例：排查"脱敏接口变慢"**

| 步骤 | 使用组件 | 操作 |
|:---|:---|:---|
| 1 | **Metrics** | Grafana 发现 `/v1/privacy/mask` P99 延迟从 200ms 涨到 3s |
| 2 | **Traces** | Jaeger 中抽样查看慢请求，发现耗时集中在 `NER` Span |
| 3 | **Logs** | 搜 `trace_id` 找到 NER 模型加载失败的 WARN 日志 |
| 4 | **Metrics** | 确认 `privacy_classification_ner_total{status="error"}` 突增 |
| 5 | 根因定位 | ONNX Runtime 模型文件损坏，导致 NER 层降级走 LLM，LLM 信号量排队 |
| 6 | 修复 | 重新加载 NER 模型，LLM 并发恢复正常 |

### 6.8 验收标准

> ✅ **Prometheus 指标暴露**：Python `/metrics` 与 Go `/metrics` 均可抓取，包含请求计数、延迟直方图、隐私原语操作计数  
> ✅ **全链路追踪**：各服务日志中均输出一致的 `X-Request-ID`  
> ✅ **DDoS 防护**：所有 Go 服务启用多层中间件（含日志记录）

### 6.9 一句话总结

> **Metrics 告诉你"哪台机器有问题"，Logs 告诉你"具体发生了什么"，Traces 告诉你"请求在哪个环节卡住了"——PrivShield 通过 Prometheus + 结构化日志 + OpenTelemetry + Grafana 的四层体系，将这三个维度的数据用同一个 TraceID 贯通，实现从"发现问题"到"定位根因"的分钟级闭环。**
