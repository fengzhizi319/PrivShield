# 数据分类分级模块 — 工业化评审文档

> 本文档是可直接填写、可复用的评审记录模板，同时给出评审依据、原理与详细审核标准的完整说明，可独立于 [design.md](design.md) 使用。方法论的原始论证仍见 design.md 第 13、14、15 章：
>
> - 第 13 章：能力导向评分维度与口径（是什么）。
> - 第 14 章：证据驱动准入模型、发布门禁与 SLO（怎么证明达标）。
> - 第 15 章：风险加权、证据时效与机器可读评分卡（如何按风险调整并自动化）。
>
> 本文档在此基础上补充了每条规则"为什么这样设计"的依据说明，以及每个评分维度可直接执行的详细审核标准，评审人无需反查 design.md 即可完成评审。

## 1. 适用范围

本文档适用于对 `privacy_local_agent/privacy/classification*` 及其 REST/gRPC 接入层（`classification_routes.py`、`classification_service.py`、`classification_grpc.py`）的以下场景评审：

- 新版本发布前的准入评审（Release Gate Review）。
- 规则集（`rule_set_version`）或合规模板变更后的复审。
- 生产事故复盘后的补充评审。
- 定期（建议每季度）成熟度复评，用于跟踪证据是否过期、技术债是否收敛。

不适用于：单元测试期间的临时自查（应使用 `make test`/`make lint` 快速反馈，无需走完整评审流程）。

## 2. 评审依据

本节说明评审框架的外部依据来源，避免评分标准成为主观判断。

| 依据来源 | 对应关系 | 用途 |
|---|---|---|
| ISO/IEC 25010 软件产品质量模型 | 功能适合性、性能效率、可靠性、安全性、可维护性、兼容性八大特性 | [第 9 节](#9) 六维度的分类边界与命名依据 |
| Google SRE（SLI/SLO/错误预算） | 用可测量的服务水平指标替代模糊的"稳定"描述 | [第 7 节](#7)、design.md 14.6 的 SLO 与告警处置 |
| OWASP ASVS / OWASP Top 10 | 输入校验、日志脱敏、认证鉴权、依赖漏洞管理 | [第 5 节](#5) 安全类门禁与安全运营维度审核项 |
| SonarQube 质量门禁模型 | 用阈值（覆盖率、复杂度、重复率）而非主观印象判定代码质量 | 可维护性维度审核标准 |
| CMMI 过程成熟度 | 流程标准化、证据可追溯、持续改进闭环 | [第 1 节](#1) 评审触发条件、[第 11 节](#11) 记录归档要求 |
| 等保 2.0 / GDPR / JR/T 0197 / GB/T 35273 | 合规模板与数据分级要求 | 安全运营维度中"合规性"审核项、`ClassificationParams.template` 相关证据 |
| 本仓库现有实现（`AGENTS.md`、design.md 第 1~12 章） | 三层漏斗架构、复合规则、异步任务、复核闭环、可观测性指标的既有设计 | 各维度审核标准中的"本模块对应实现"参照点 |

**为什么不采用纯人工经验评分**：经验评分依赖评审人个体的知识水平与心情波动，无法跨版本比较，也无法在事故复盘时还原"当时为什么判定通过"。采用外部标准 + 证据链接，可以让不同评审人在相同证据下得出一致结论，并支持事后追溯。

## 3. 评审原理

以下原则决定了本文档各节的顺序与强制性，评审时应按此优先级执行，不可颠倒。

1. **证据优先于陈述（Evidence over Assertion）**：任何分数必须附带可复现的证据链接（测试报告、基准 JSON、扫描结果）。没有证据的"应该没问题"不能计分，缺证据的子项记 0 分。
2. **门禁优先于均分（Gates over Averages）**：先判定 [第 5 节](#5) 的一票否决项，再计算加权分数。原因是加权平均会被高分维度稀释安全或正确性缺陷——例如功能、性能、工程化都是 9 分，但存在敏感数据泄露，总分仍可能高于 7 分及格线，这与实际风险严重不符，因此安全底线必须独立于平均分判断。
3. **版本绑定（Bound to an Immutable Release）**：评审对象必须是一个不可变的发布候选（commit SHA 或镜像摘要），不允许"评审整个项目现状"这种无法复现的模糊范围，否则无法在复审时确认改动是否针对同一基线。
4. **风险即权重（Risk as Weight）**：不同模块处理的数据敏感度不同，同一分数在低风险模块和高风险模块（涉及 L5 基因组/生物特征数据）代表的实际风险不同。[第 6 节](#6) 的权重调整让高风险模块的安全与可靠性分数对总分影响更大，避免"性能好、安全差"的模块蒙混过关。
5. **时效即衰减（Freshness as Decay）**：规则集、依赖库、模型权重、攻击面会随时间漂移，陈旧证据会带来虚假信心。[第 7 节](#7) 要求证据标注生成时间与过期规则，过期证据不能沿用旧分数。
6. **责任到人（Accountability by Role）**：每个维度必须有明确的 Accountable 签署人（见 [第 10 节](#10-raci)），评分不是"审核工具自动生成的数字"，而是责任人对该数字负责，防止评审流于形式。
7. **可复现（Reproducibility）**：证据必须能被第三方使用相同命令重新生成并得到一致结论（例如 `make test-cov`、`tests/benchmark_classification.py`），而不是评审人私下手动验证后仅口头确认。
8. **零知识扫描优先（Zero-Knowledge First）**：评审过程本身产生的制品（测试报告、日志摘录）不得包含真实敏感数据，只能使用合成或脱敏数据，这与模块本身的 Zero-Knowledge 扫描原则（design.md 3.5）保持一致，避免评审流程本身成为新的泄露面。

## 4. 使用说明

1. 每次评审对应**一个不可变的发布候选版本**（commit SHA 或镜像摘要），不得跨版本合并评分。
2. 先完成 [第 5 节：发布门禁](#5)，任一门禁未通过则**禁止发布**，无需再计算加权分数。
3. 门禁全部通过后，按 [第 6 节：风险分级](#6) 确定权重表，再按 [第 8 节：详细审核标准](#8) 逐项打分，填入 [第 9 节：加权评分](#9)。
4. 所有分数必须附带证据链接（测试报告、基准 JSON、扫描结果等），不得凭印象打分。
5. 按 [第 10 节：签署矩阵](#10-raci) 完成责任人签字后，评审记录归档到 `artifacts/classification/<release_id>/review.md`。
6. 证据有条件失效，见 [第 7 节：证据与时效](#7)；过期证据对应维度自动降级，不得沿用旧分数。

## 5. 发布门禁（一票否决）

任一未通过即禁止发布，不参与加权平均。例外必须记录风险说明、影响范围、补偿控制、审批人与失效日期，到期自动恢复为阻断项。每项门禁的判定依据见下表"设计依据"列。

| 门禁 | 通过条件 | 设计依据 | 证据 | 结果（PASS/FAIL） |
|---|---|---|---|---|
| 敏感数据泄露 | 日志/指标/trace/导出制品未包含原始测试敏感值（canary PII 扫描） | Zero-Knowledge 扫描原则（design.md 3.5）；OWASP 日志脱敏要求 | | |
| 规则集可追溯 | 结果可关联 `rule_set_version`、参数来源与时间戳 | `AuditInfo` 审计追溯设计（design.md 3.3、10.4） | | |
| Golden set 核心正确性 | 版本化 golden set 中 L5 不漏报，其他标签达约定阈值 | 分类错误直接导致敏感数据误判为低敏感度，风险不可逆 | | |
| 依赖与代码安全 | 无未豁免的高危/严重漏洞，密钥扫描通过 | OWASP Top 10（A06 易受攻击组件）、供应链安全 | | |
| 可恢复运行 | 可选 ML 依赖/模型/推理失败时服务仍可启动并按文档降级 | 三层漏斗降级设计（design.md 第 9 章） | | |
| 接口兼容 | REST/gRPC/Pydantic 契约与发布说明一致 | 避免下游调用方因契约漂移而产生静默错误 | | |

风险接受记录（如有）：`<issue 链接 / 无>`，失效日期：`<date>`

## 6. 风险分级

按模块在正常路径中可能接触到的最高 `SensitivityLevel` 判定风险等级，并选用对应权重表。判定依据：处理数据的敏感度上界越高，安全与可靠性缺陷的影响半径（blast radius）越大，因此对应维度权重应上浮（原理见 [第 3 节第 4 条](#3)）。

| 风险等级 | 判定依据 | 本仓库典型模块 |
|---|---|---|
| 高（涉及 L5） | 直接处理基因组、生物特征或多字段组合升级结果 | `classification_llm.py`、`classification_composite.py`、`classification_rule_engine.py` |
| 中（涉及 L4） | 处理身份证、病史等高风险字段，不直接处理基因组 | `classification_ner.py`、`classification_async.py` |
| 低（≤ L3） | 仅处理配置、模板、聚合结果 | `classification_utils.py`（模板部分）、`classification_models.py` |

**本次评审对象风险等级**：`<低 / 中 / 高，填写判定理由>`

## 7. 证据与时效

填写证据生成时间与失效窗口，展示评分时必须同时展示证据年龄。过期规则的设计依据见 [第 3 节第 5 条](#3)：软件、依赖与威胁面会随时间漂移，证据本身有保质期。

| 证据类型 | 生成时间 | 建议新鲜度窗口 | 过期原因 | 是否过期 | 制品路径 |
|---|---|---|---|---|---|
| Golden set 正确性报告 | | 90 天 / `rule_set_version` 变更即失效 | 规则集变更后旧样本不再代表当前逻辑 | | `artifacts/classification/<release_id>/unit-test.xml` |
| 性能基准（p95/p99/吞吐） | | 90 天 / 依赖或硬件变更即失效 | 依赖库/模型/硬件规格变化会改变延迟分布 | | `artifacts/classification/<release_id>/benchmark.json` |
| 安全扫描（SCA/SAST/secret scan） | | 30 天 | CVE 库持续更新，旧扫描可能遗漏新披露漏洞 | | `artifacts/classification/<release_id>/security-scan.json` |
| 泄露 canary 回归 | | 涉及日志/指标/导出逻辑改动即需重跑 | 日志/指标代码路径变更可能引入新的泄露点 | | `artifacts/classification/<release_id>/security-scan.json` |
| SLO/告警演练记录 | | 180 天 | 告警规则或运行手册可能与实际系统行为脱节 | | `artifacts/classification/<release_id>/observability-check.json` |

## 8. 详细审核标准（六维度）

本节将 [第 9 节](#9) 的六个维度展开为可直接执行的打分细则，每个维度给出 0/3/5/7/9~10 分的判定标准与具体检查项，避免评审人凭主观印象定分。评分区间总口径：1~2 分缺失或存在反向实现；3~4 分具备基础实现但关键路径有缺口；5~6 分达到可用水平但边界证据不足；7~8 分实现完整、可追溯；9~10 分标准化且可作为标杆。

### 8.1 功能质量 F

| 检查项 | 0 分（不通过） | 5 分（可用） | 9~10 分（标杆） |
|---|---|---|---|
| 三层漏斗正确性 | 无法验证 Layer-1/2/3 触发条件，或存在漏判 L5 的已知问题 | 主路径（规则命中、NER 触发、LLM 触发）有测试覆盖，边界条件未系统验证 | 版本化 golden set 覆盖字段/记录/表三级、全部规则 ID 与合规模板，且 L5 漏报为 0 |
| 规则准确性 | 身份证/医保卡等校验和逻辑无测试或曾发现误报 | 校验和逻辑有单元测试，未覆盖边界值（如全 0、全 9） | 覆盖正例、边界值、已知误报案例的回归测试全部通过 |
| 复合规则/多引擎协同 | `CompositeRuleEngine` 未测试或存在字段组合误判 | 内置默认复合规则有测试，自定义规则路径未验证 | 默认规则、自定义规则、Layer 间不遗漏不冲突均有回归测试 |
| 输入格式与降级覆盖 | 仅验证 JSON 单一输入，DataFrame/Arrow/SecretFlow 路径无测试 | 主要格式有冒烟测试，异常输入（空值、超长文本、二进制）未系统覆盖 | 全部输入格式、空值、超长文本、图片/二进制均有专项测试且结果符合预期 |

**证据来源建议**：`tests/classification/test_classification.py`、`test_classification_composite.py`、`test_classification_vectorized.py`、`test_classification_templates.py`。

### 8.2 性能 P

| 检查项 | 0 分 | 5 分 | 9~10 分 |
|---|---|---|---|
| 延迟测量方法 | 无基准测试，仅有设计目标描述 | 有基准脚本但未固定环境/未区分冷热启动 | 固定环境、预热后运行、区分 p50/p95/p99，与 CPU/内存峰值一并报告 |
| 规则路径延迟 | 未测量 | 有粗略耗时数据 | p95 ≤ 5ms，p99 ≤ 10ms，连续 3 次运行均达标 |
| 向量化吞吐 | 未验证向量化路径与标量路径结果一致 | 吞吐量有单次测量 | ≥ 10000 行/s 且与标量路径结果完全一致，多次运行取最差值仍达标 |
| LLM/NER 延迟与超时 | 无超时保护或超时行为未测试 | 超时保护存在但未验证极端输入下是否生效 | 超时率、成功率、降级率按输入类型分组统计，且超时不阻塞主线程 |

**证据来源建议**：`tests/benchmark_classification.py`（对应 `make` 无直接目标时可用 `python tests/benchmark_classification.py` 直接运行）。

### 8.3 可靠性 R

| 检查项 | 0 分 | 5 分 | 9~10 分 |
|---|---|---|---|
| 降级容错 | 依赖缺失导致进程崩溃 | ONNX/ModelScope/PyTorch 缺失时有 NoOp 降级，但未测试 | 全部降级路径（Small-NER、LLM、SecretFlow、向量化引擎）均有故障注入测试并验证服务持续可用 |
| 并发安全 | 多线程推理无锁保护 | 有 `threading.Lock`，但未做并发压力测试 | 双重检查锁定 + 并发压测验证无显存/内存争用，无数据竞争 |
| 异步任务状态机 | 任务状态可能丢失或卡死 | 正常路径状态流转有测试，满载/重启场景未验证 | PENDING→RUNNING→DONE/FAILED 全状态覆盖，满载拒绝、TTL 清理、重启恢复均有测试 |
| 持久化一致性 | SQLite 模式未测试并发写入 | 基本读写有测试 | 并发写入、异常断电模拟、重启后数据一致性均验证通过 |

**证据来源建议**：`tests/classification/test_classification_async.py`、`test_classification_review.py`、`test_classification_real_models.py`。

### 8.4 安全运营 Sec

| 检查项 | 0 分（触发一票否决） | 5 分 | 9~10 分 |
|---|---|---|---|
| Zero-Knowledge 扫描 | 日志/指标/导出制品出现原始敏感值 | `redact` 逻辑存在但未做 canary 回归 | 注入 canary PII 后端到端扫描日志/指标/trace/导出制品均未泄露，且纳入 CI 常规回归 |
| 输入校验 | 公共入口缺少 Pydantic 校验 | 主要入口有校验，个别参数缺少边界约束 | 所有公共入口、REST/gRPC 参数均经 `model_validate`，含边界值与非法值测试 |
| 传输与鉴权 | 生产环境未启用 TLS/鉴权且无风险接受记录 | TLS/鉴权可配置但未在评审环境验证 | TLS 1.2+、API Key/mTLS 均验证生效，且有对应集成测试 |
| 依赖与代码安全 | 存在未豁免高危/严重漏洞 | 有 SCA 扫描但未纳入 CI 强制门禁 | SCA/SAST/secret scan 均纳入 CI 强制门禁，高危发现有闭环记录 |
| 合规模板 | 模板规则与声明的标准不符 | 模板存在但未做一致性回归 | JR/T 0197、GB/T 35273、GDPR 模板均有对应测试且随标准更新维护 |

**证据来源建议**：`tests/classification/test_classification_zk.py`、`test_classification_templates.py`、`test_classification_secretflow.py`，以及 CI 中的 SCA/SAST 步骤（如未接入，需在 [第 12 节清单](#12) 中登记为缺口）。

### 8.5 可维护性 M

| 检查项 | 0 分 | 5 分 | 9~10 分 |
|---|---|---|---|
| 静态检查 | `make lint`/`make typecheck` 未接入 CI 或长期失败 | 本地可通过，但 CI 未强制阻断 | CI 强制执行 `make lint`、`make typecheck`，失败即阻断合并 |
| 测试覆盖率 | 无覆盖率统计 | 有覆盖率数据但低于团队基线且无改进计划 | `make test-cov` 覆盖率达到团队基线（建议 ≥ 80%），关键模块（rule_engine/llm/composite）覆盖率单独跟踪 |
| 代码规范一致性 | 类型标注、文档字符串缺失严重 | 核心类型标注齐全，文档不完整 | type hints、双语 docstring、Execution Steps 说明齐备，评审样例见 design.md 13.9 |
| 变更可追溯 | 无法从提交记录关联需求/缺陷 | 提交信息基本可追溯 | PR 描述、测试映射、评分记录三者可互相追溯 |

**证据来源建议**：`make lint`、`make typecheck`、`make test-cov`（对应 Makefile 79~101 行现有目标）。

### 8.6 工程化 E

| 检查项 | 0 分 | 5 分 | 9~10 分 |
|---|---|---|---|
| 可观测性覆盖 | 关键路径无 Counter/Histogram | 主路径有埋点，边界事件（超时、降级）未覆盖 | Counter/Histogram/Gauge 覆盖全部关键路径（design.md 第 10 章 15 个指标），且标签不含敏感信息 |
| SLO 与告警 | 未定义 SLO 或从未演练告警 | SLO 已定义，告警未实际触发验证 | 每项关键 SLI 有 SLO、告警阈值、处置动作，且近 180 天内演练过一次 |
| CI/CD 可复现 | 手工发布，制品不可追踪 | CI 存在但产物与评审证据未关联 | CI 自动产出 [第 8 节](#8) 所需全部证据制品，评分可半自动生成（参见 design.md 15.4 机器可读评分卡） |
| 版本与回滚 | 规则集变更无版本号或无法回滚 | `rule_set_version` 有记录，回滚流程未演练 | 影子模式 + 版本化参数支持无风险灰度与快速回滚 |

**证据来源建议**：Prometheus `/metrics` 输出、Grafana 告警记录、CI pipeline 配置、`shadow_mode` 相关测试（`test_classification_shadow.py`）。

## 9. 加权评分

按 [第 6 节](#6) 判定的风险等级选择对应权重列，并依据 [第 8 节](#8) 的检查项逐项打分。得分范围 0~10；缺少证据的子项记 0 分，不允许标记"未评估"跳过。

$$
S = w_F \cdot F + w_P \cdot P + w_R \cdot R + w_{Sec} \cdot Sec + w_M \cdot M + w_E \cdot E
$$

| 维度 | 低风险权重 | 中风险权重 | 高风险权重 | 得分（0-10） | 加权得分 | 证据链接 |
|---|---:|---:|---:|---|---|---|
| 功能质量 $F$ | 25% | 20% | 15% | | | |
| 性能 $P$ | 15% | 15% | 10% | | | |
| 可靠性 $R$ | 15% | 20% | 25% | | | |
| 安全运营 $Sec$ | 10% | 15% | 25% | | | |
| 可维护性 $M$ | 20% | 15% | 12.5% | | | |
| 工程化 $E$ | 15% | 15% | 12.5% | | | |
| **加权总分 S** | 100% | 100% | 100% | | | |

### 结论分级

| 加权总分 | 结论 |
|---|---|
| 9.0~10.0 | 标杆（Benchmark） |
| 7.0~8.9 | 通过（Pass） |
| 5.0~6.9 | 有条件通过（Conditional），需列出缺口与复验日期 |
| 1.0~4.9 | 不通过（Fail） |

## 12. 最小行动清单

当前评审若发现以下常见缺口，应登记为待办并指定负责人与完成日期，而非默许通过：

1. 缺少版本化 golden set：需为规则、模板、复合规则建立带标注的合成数据集并接入 CI。
2. 未接入 SCA/SAST/secret scan：需在 CI 中新增依赖与代码安全扫描步骤。
3. 性能目标缺少可复现基准：需将 `tests/benchmark_classification.py` 的输出固化为 JSON 制品并归档。
4. SLO/告警未演练：需至少完成一次故障演练并记录处置结果。
5. 证据未关联 `release_id`：需在制品目录 `artifacts/classification/<release_id>/` 下归档，避免证据与版本脱节。
